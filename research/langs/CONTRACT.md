# An opt-in boundary contract: design study

An independent design review (2026-10-30), read-only against main c57c8ee, of what an opt-in macro, attribute or DSL per language would add on top of the inferred boundary and comment laws. Its recommendation: no ten macros; one shared opt-in contract, piloted as a TypeScript CI analyzer, built only if the pilot passes the falsification bar in "Build order and falsification". Not built.

## What the opt-in can honestly guarantee

The valuable addition is a **closed-boundary contract checked in the user's normal build or a mandatory CI job**, not a second way to run the existing check. Its promise should be precise: for a named entry, under a specified build configuration and a deliberately restricted call model, every syntactically reachable call is either (a) a known intrinsic with specified semantics, (b) an in-scope helper whose body is recursively inspected, or (c) explicitly classified as `answer`, `skip`, or a store operation. Adding an unclassified call anywhere in that inspected closure is an error, including in a branch not exercised by tests. The checker rejects unresolved calls and unsupported constructs rather than calling them covered. An empty declaration means no external calls, not “infer the rest.”

This is not a guarantee about arbitrary code. Indirect calls, overrides, reflection, monkey patches, native code, generated code, macros, conditional compilation, callbacks, globals, constructors, operators, implicit conversions, destructors, async tasks and transitive helper calls must either be resolved and checked under the exact build configuration, covered by an explicit abstraction, or rejected. If a language's build cannot install such a checker, the guarantee exists only in a required CI gate—not at compile/load time. A contract on an interface does not by itself prevent a method from calling `File.write` directly. Linker undefined-symbol checks and typed dependencies do not close that hole either. Dynamic languages cannot generally promise that later runtime mutation will not change behavior.

Coverage is also not semantic soundness. `skip` asserts that omitted effects are irrelevant; `answer` abstracts the result but must not secretly mutate rule state; store declarations omit real-world behavior such as eviction. Types and compile-time closure cannot prove those assertions. The existing executor refuses an unstated call given a state reference, but a tag or an explicit statement is a user assumption (`core/extract-step.ts:833-849`); its write scan is conservative, not a general effect proof (`core/extract-step.ts:863-925`). Running both versions on sampled requests is evidence, not exhaustive equivalence. Proofs remain conditional on the abstraction and model; refutations may depend on an impossible answer. Do not market “all calls covered” as “all effects verified.”

The present mechanism already provides the right common target: `StepOptions` carries explicit answers/skips/stores and strictness (`core/extract-step.ts:59-66`); an `Answer` records a key, type and sites (`core/extract-step.ts:116-123`); untyped inference is refused (`core/extract-step.ts:964-975`); check requests carry answers by key (`core/extract-step.ts:2675-2706`). In particular, one callee is answered at most once per step (`core/extract-step.ts:805-808`), and only supported scalar/optional sorts qualify (`core/extract-step.ts:162-163`). A typed contract must not imply that overloads, repeated calls, arbitrary objects, failure channels, or stores are supported before the extractor and harness support them. Current call-site replacement uses source spans (`core/extract-step.ts:2171-2198`); it is a check-time copy, not a production guard.

## Shared structure: one contract, native front ends

Call the proposed structure a **boundary contract**. It has an entry; a closed set of typed callee identities, each classified as `answer`, `skip` or `store` (with get/set/delete and key/value semantics); and typed laws over an explicitly defined state/request/result view. This is an adapter into the current IR, not a new prover or a requirement that production calls pass through a GDP wrapper. A language-native expression names symbols wherever its tooling can resolve them; canonical qualified `Answer.key` strings are derived, not handwritten. Store the exact symbol/signature, source span and build configuration for diagnostics, then map to today's harness key. Detect collisions—especially overloaded methods, aliases and distinct symbols with the same current key—and refuse rather than silently merge. Symbol identity within a build is not a stable cross-build identifier: regenerate the derived key after a rename and check it against the harness's own naming.

A source-level checker walks **all** relevant entry bodies and helpers, not only paths the symbolic executor happened to visit. Intrinsics are a small versioned allowlist with modeled semantics, not all standard-library calls. It reports the location, resolved callee, entry-to-call chain and suggested declaration. It rejects missing bodies and unknown dispatch, and checks calls hidden in expressions and generated/expanded code where the language's compiler can expose them. Enumerate required targets, feature flags, build tags, profiles and generated-source steps in CI; a green result is scoped to that matrix. The check must be wired into the real build or a non-optional CI job, fail on missing tooling, stale generated files or analysis errors, and run on the same source/compiler options that ship. A source-only approximation that misses expansion is not entitled to the stronger claim.

**Composition:** no contract means exactly today's inferred boundary and existing comment laws. With a contract, validate it first and use it as a closed-world constraint: explicit contract classifications win; an unlisted boundary call is an error even if inference would have skipped or answered it. Inference can still classify internal modeling details and suggest declarations; it may not widen a closed contract. Existing API options and boundary tags must agree with it or produce a conflict error, not silently override it. Comment laws remain available and independent; a typed law and a comment law with the same identity must either normalize identically or be rejected as a duplicate. Do not assume the other agent's CLI/comment implementation is already merged. A contract must be read from source or a fresh compiler-produced manifest, then normalized into the existing options/IR and the same `Answer.key` protocol. Production never needs the harness stub.

**Typed laws:** use real expressions, not strings, and typecheck a pure, nonexecuted law function over a documented `before`, `after`, `input`, `result` and parameter view as appropriate to the law kind. The reader must lower the expression into the prover's existing law vocabulary; a successfully typed but unsupported construct is a clear refusal. Types and rename tooling check references, not truth or purity; the checker enforces the supported pure expression subset. Compiling a normal function that is never called is often the simplest mechanism, but it is not automatically compiled out in every toolchain. A source-only test/sidecar file checked by CI gives stronger zero-production-cost behavior. String comments and Java/Kotlin annotation strings do not gain expression typechecking or rename safety merely by being annotations.

Illustrative TypeScript sidecar—not a shipped API—might contain `boundary(Rule, { answer: [readQuota], skip: [log] })` and `law<Snapshot>('cap', s => s.used <= s.limit)`. `boundary` and `law` are type declarations for the analyzer; the sidecar is in a `tsc --noEmit`/contract-check project and is not imported or bundled in production. The checker resolves the actual symbols, follows the rule's helper closure, and compares calls to that list. A full build must still typecheck the production code. An interface member or method reference is a symbolic identity, not a claim that every possible implementation is pure. For private fields, a sidecar may need a user-provided public/read-only snapshot type or a same-class law; do not generate privileged access and pretend the IDE has checked it.

## Language decisions

Estimates below are rough, incremental **uncompressed source bytes**, not measured package sizes or commitments. They include a small adapter and representative diagnostics/tests only where stated; compiler-plugin distribution, compatibility matrices and maintenance can exceed the code. Production bytes/runtime depend on actual build settings and must be measured. All estimates reuse the shared contract engine and current extraction/harness; no estimate includes a new prover. Each entry's guarantee is the closed-world guarantee above, not a claim that the named macro alone detects every call.

### Rust

- **Least:** an opt-in `#[gdp::rule]` on a function/impl plus a typed boundary trait (or explicitly listed paths) and ordinary typed law functions in a `#[cfg(...)]` module; for example, `trait Deps { fn quota(&self, id: u64) -> u32; }`, with the rule calling a `Deps` method. No per-call `// gdp: answer u32`: the reader obtains the return from the trait's signature once. A body that calls a different path directly still needs detection. If the project already has such a trait, the added user text can be just its classification and laws.
- **Mechanism/cost:** borrow `mockall::automock` for generating test doubles and a proc-macro for marking/validating the local syntactic subset; an ordinary generic trait can monomorphize without GDP runtime, while a trait object uses ordinary dynamic dispatch. Proc macros are build dependencies, not shipped runtime dependencies. `#[doc = "gdp: ..."]` is parseable stable metadata but remains a string, with no expression typing or rename support. A `cfg`-only law has no production code only if CI explicitly builds/checks the law configuration.
- **Enforcement:** a `syn` proc macro sees tokens, not rustc name/type resolution or all expanded helper bodies; it cannot honestly establish a general resolved call closure. For an initial enforceable version, restrict the annotated body to an explicit DSL/capability form and reject unknown macros, indirect calls and helpers it cannot inspect; otherwise require a dedicated compiler-aware CI analyzer, with rustc/rust-analyzer version risk. Cargo compilation checks trait signatures; the analyzer checks completeness. Neither alone supplies both properties.
- **Reader/composition:** read source trait method signatures and marker/typed law AST, resolve the dependency field/method to the existing qualified key, emit `ret` and contract metadata. The current Rust reader is syn-based and records call spans (`core/rs/src/main.rs:1-6,322-324`); its check currently rewrites calls to `__gdp_answer` (`core/extract-rs.ts:235-238`). A proc macro cannot query the inferred type of an arbitrary external expression: a named typed interface or compiler-derived sidecar is necessary. Unsupported return kinds still refuse.
- **Prior art/risk/cost:** mockall, proc macros, doc attributes. Roughly 12–25 KB Rust adapter/macro plus 5–10 KB reader glue; a rustc-integrated checker could be substantially larger and brittle. Trait refactoring, generic/associated return types, macro expansion and alternate cfgs make this a poor first pilot. No universal removal of tags for untyped/unresolved calls.

### Go

- **Least:** a small interface already injected into the rule, e.g. `type Quota interface { Read(string) int }`, plus a separate contract naming `Quota.Read` and typed law functions in a CI-only Go file. Otherwise a marker comment on the rule and a typed symbol list in the sidecar; direct external calls are allowed only when listed.
- **Mechanism/cost:** a `go/analysis` pass using `go/packages`/`go/types` walks resolved calls; gomock or counterfeiter illustrate interface-driven mocks, not closure enforcement. No production dependency or runtime cost if the analyzer and laws are CI-only. Generate/compile a temporary typed law package or include a non-shipping build-tagged law file; a build tag that CI forgets is not enforcement.
- **Enforcement:** a mandatory analyzer invocation (`go vet` with the analyzer or equivalent CI) for each relevant GOOS/GOARCH/tags, plus ordinary Go compilation. `go generate` alone is optional and cannot fail a normal build if never run. Reject unresolved function values/interface dispatch unless bounded and explicitly modeled; follow package helpers. Contract declarations by themselves don't prohibit direct imports.
- **Reader/composition:** `core/go/reader.go:1-5` already obtains Go types, though it notes external non-stdlib imports may be invalid; use a build-aware package loader or emit a fresh manifest, not a guessed type. Normalize interface methods/signatures into `ret` and boundary entries. Keep the existing harness overlay (`core/extract-go-check.ts:324-331`) and current inferred behavior for unmarked rules.
- **Prior art/risk/cost:** gomock/counterfeiter and go/analysis; roughly 15–30 KB Go analyzer + 4–8 KB adapter. Whole-program dynamic dispatch, third-party package loading, build tags, generated sources and distinguishing semantic intrinsics from unlisted calls dominate risk.

### C

- **Least:** a marker on the entry and a typed list using declared function addresses, e.g. `GDP_ANSWER(quota_read)` / `GDP_SKIP(log)` in a separate analysis-only contract; a law is an ordinary typed `bool` function over an explicit snapshot struct. Macros can expand to no code in production but cannot themselves inspect the function body.
- **Mechanism/cost:** a clang-based AST check run with the real `compile_commands.json`, types, includes and defines. Use function declarations/address expressions to typecheck signatures and make IDE rename possible; linking a never-called law still may retain code, so compile the contract separately with syntax-only checks. No GDP runtime if contract definitions are excluded from shipping artifacts.
- **Enforcement:** required clang analysis per translation unit and macro/configuration; unknown function pointers, inline assembly, indirect calls and missing body/headers fail closed. A custom clang plugin integrated into compilation can fail the build, but an external mandatory CI pass is simpler and is only a CI guarantee. `ld --wrap` is useful prior art for substituting selected link-visible symbols in checks, not for detecting all calls: it misses or behaves differently for inlining, internal/static calls and some same-unit references and is linker-specific.
- **Reader/composition:** the existing clang JSON reader already uses the project's flags and lowers through Go's typed shape (`core/c/reader.ts:1-13`); read declarations/law AST and classify resolved call declarations. The current harness rewrites a copy and casts `gdp_answer` to the result type (`core/extract-c.ts:326`); it remains the execution mechanism. Preprocessing can erase marker syntax, so retain source spelling or produce a compiler-side manifest.
- **Prior art/risk/cost:** clang tooling and `--wrap`; roughly 15–35 KB analyzer/adapter. Macros and build variants, function-pointer targets, unspecified evaluation order, UB and linker differences make broad coverage expensive. Headers alone are not complete call graphs.

### C++

- **Least:** the C-style marker plus typed member/function references, e.g. a casted `&Quota::read` when overloaded, and a `constexpr` or ordinary typed law over a snapshot. Prefer existing injected interfaces; do not require replacing direct production calls solely for GDP.
- **Mechanism/cost:** clang AST analysis after template instantiation, using the same compilation database. A `constexpr` function is typechecked but not guaranteed absent from the binary; put contracts/laws in an analysis-only translation unit for zero GDP runtime. Ordinary interface dispatch, if newly introduced, may itself have a production cost.
- **Enforcement:** mandatory clang pass on each actual instantiated translation unit/configuration; reject unknown virtual targets, unresolved dependent calls, template instantiations not analyzed, function pointers and unsupported implicit calls. Uninstantiated templates are not covered merely because their definitions compiled.
- **Reader/composition:** extend `core/c/reader.ts` and the C/C++ front end for typed declaration identities, explicit instantiations and laws; existing support explicitly refuses virtual dispatch at call sites (`core/c/reader.ts:440`). Respect the current filtered-dump scope; a full compiler analysis may need more than the extraction reader sees. The existing copy-based check stays unchanged.
- **Prior art/risk/cost:** clang tooling, `--wrap` with C's caveats, dependency-injected mocks; about 15–30 KB incremental over C, potentially much more for templates/virtuals. Overloads, operator/destructor calls, ADL, build complexity and compiler compatibility argue against early investment.

### Ruby

- **Least:** for an already typed project, one RBS or Sorbet interface for the dependency, classifying e.g. `Quota#read` once, and a typed law method in a non-shipping check file. Otherwise the author must write at least a result type once; there is no sound automatic return-type oracle for arbitrary dynamic Ruby. This removes *per-call* tags, not type declarations altogether.
- **Mechanism/cost:** Prism source analysis with a closed DSL or injected interface; RBS + Steep or Sorbet for optional static signature/type checks. A Ruby DSL loaded with the application costs a gem/load-time work; a source-only CI contract has no GDP production dependency or cost. `Module#prepend` is useful for harness stubs, not a production completeness proof.
- **Enforcement:** required CI typecheck and conservative source analyzer, or an opt-in load-time macro that validates only its restricted local source. Fail on `send`, `eval`, unknown receiver types, dynamic definition and monkey-patching in the claimed scope. Even then a later monkey patch can invalidate a load-time result; Ruby alone cannot give a general compile-time guarantee. RBS is a declaration, not a runtime guarantee that an implementation returns its declared type; enforce/test conformance separately or state it as an assumption.
- **Reader/composition:** `core/rb/reader.rb:1-8` uses Prism and infers ordinary state types, not external returns; add RBS/Sorbet signature lookup and map declared methods to existing keys. The reflective harness already has answer/store stubs (`core/rb/harness.rb:41-45,164-166`). Existing inferred and comment-only rules remain untouched.
- **Prior art/risk/cost:** RBS/Steep, Sorbet, reflective mocks; roughly 12–25 KB adapter/analyzer excluding the typechecker. Signature drift, overloads, dynamic dispatch and missing types mean this is not a zero-annotation solution or a sound global Ruby type system.

### Elixir

- **Least:** one behaviour callback for a dependency, e.g. `@callback quota(binary()) :: non_neg_integer()`, plus a boundary classification and an ordinary typed law function over a state struct. Calls through an injected module/behaviour replace repeated answer tags; if the callback already exists, classify it once. An untyped arbitrary remote function still needs a declaration.
- **Mechanism/cost:** borrow Mox's behaviour contracts and test doubles; an opt-in macro can inspect/rewrite a restricted quoted rule body and emit compile-time errors for unlisted remote calls. A Mix compiler/CI analyzer can inspect a larger closed source scope. The macro package is a compile-time dependency; Mox is test-only if used. A production behaviour/module indirection is ordinary runtime dispatch, not automatically zero-cost. Compile law files only in CI for no production GDP code.
- **Enforcement:** compile time only for syntax the macro actually owns and traverses, including expanded macros it can account for; otherwise mandatory Mix/CI checking. Reject dynamic `apply`, unresolvable module expressions and helpers/macros outside the analyzed closure. Behaviours verify callback presence/arity, not return types or semantic conformance; `@spec` and Dialyzer provide useful success typing but not a sound compile-time return-type proof. Runtime checks are a separate tradeoff.
- **Reader/composition:** `core/ex/reader.exs:1-8` already parses quoted syntax but infers its own types; add behaviour/@callback/@spec lookup for supported scalar result types and lower typed law AST. The harness rewrites remote call AST to `GdpAnswer.a` (`core/ex/harness.exs:18-40`); source-level contract metadata maps to those same keys. Current no-store restriction remains.
- **Prior art/risk/cost:** Mox behaviours, `@callback`, `@spec`, Dialyzer and quoted macros; roughly 10–22 KB Elixir plus 3–6 KB glue. Source expansion, behaviour indirection, ambiguous specs and runtime contract violations are the risks; no claim that `@callback` enforces a value's type.

### Java

- **Least:** an injected interface and an analysis-only class containing symbol-bearing method references and boolean law methods, with a marker annotation on the rule or an external entry declaration. `@GdpLaw("...")` remains a convenient comment-like notation, but its string is not a Java expression and IDE rename will not update field references inside it.
- **Mechanism/cost:** a javac plugin or a build-integrated source analysis using `Trees`/attributed symbols; JSR 269 annotation processing can discover markers and generate typed helpers but must not be assumed to provide complete attributed method-body call analysis in all compiler phases. For production-free GDP dependencies put the annotations/contract and law compilation on an analysis-only path, or use SOURCE-retention annotations with an explicit compile-only dependency; annotation metadata/source-only laws need not ship.
- **Enforcement:** the javac plugin can fail the real compilation when reliably installed; otherwise a required CI analysis with identical classpath/source level. Recursively inspect helper bodies; reject reflection, native bodies, unbounded interface/virtual dispatch and unavailable sources unless explicitly abstracted. A generated interface/mock does not prevent an unrelated static call.
- **Reader/composition:** javac already attributes calls and emits declaring owner, result and spans (`core/jvm/JavaReader.java:1-3,795-812`); integrate symbol references and typed law methods there or consume the checker's fresh manifest. The current JVM checker rewrites call sites or uses interface proxies; prebuilt classes cannot generally be rewritten (`core/extract-jvm.ts:139,170-171`; `core/jvm/Harness.java:31-48`). Keep annotations/comments optional.
- **Prior art/risk/cost:** annotation processing, javac Trees, mocking/injected interfaces; around 15–30 KB JVM analysis and 4–8 KB glue. Compiler phase and JDK compatibility, overloads, Lombok/other generated code, and classpath completeness are substantial risks.

### Kotlin

- **Least:** same interface + symbol references/typed law functions as Java, preferably in a CI-only source set. A typed lambda law such as `(Snapshot) -> Boolean` is IDE-renamable; an `@GdpLaw` string is not. Keep the marker optional.
- **Mechanism/cost:** KSP can discover declarations and generate typed adapters from interface signatures, but it is not a general resolved-body call analyzer. Completeness requires a K2 compiler plugin or a separate analysis tool using an appropriate resolved analysis API. A compiler-only dependency and analysis-only law source add no GDP production runtime; newly introduced interface dispatch is ordinary production behavior.
- **Enforcement:** compiler plugin in every shipping compilation, or required CI with the same Kotlin compiler/configuration. Resolve extension functions, properties/getters, overloads, inline functions and generated source; reject unavailable or dynamically dispatched targets. A KSP-generated mock alone does not establish closure.
- **Reader/composition:** the present reader uses PSI plus locally reconstructed types rather than full K2 analysis (`core/jvm/KtReader.java:1-5,936-946`); consume a compiler-resolved manifest or extend it carefully rather than pretending PSI provides every resolved type. Map to the JVM harness keys and leave current inference/comment laws intact.
- **Prior art/risk/cost:** KSP for metadata, compiler plugins for resolved bodies; roughly 20–45 KB plus 4–8 KB adapter, with high Kotlin-version maintenance. Suspend/inline expansion, multiplatform targets and K2 API churn are major risks.

### TypeScript and Effect

- **Least:** a no-emit `.gdp.ts` sidecar with symbol-bearing `boundary(...)` and typed law lambdas over a snapshot; one boundary entry per callee, not per call. An existing injected interface or Effect service tag supplies method types; no decorator is required. A marker decorator can improve discoverability, but needs syntax/runtime settings and does not inspect method bodies or enforce completeness.
- **Mechanism/cost:** a TypeScript compiler-API checker, run as a mandatory build/CI step, resolves aliases and walks source plus helpers. The sidecar imports types with `import type` where possible and is not emitted/bundled; GDP has no production runtime dependency or cost. `tsc` itself does not run arbitrary custom semantic plugins as a standard enforcement mechanism; an editor plugin or decorator alone is not a build gate.
- **Enforcement:** a required analyzer plus ordinary `tsc` for each actual tsconfig/project reference. Reject `any`, unresolved computed properties, dynamic import/require, unchecked callbacks and unbounded polymorphism in the covered closure. Refuse uncertain analysis rather than letting TypeScript's structural types imply an effect system. Code emitted by a different transpiler/configuration needs the same source/configuration coverage.
- **Reader/composition:** TypeScript uses a separate executor, not `Stepper`; it currently recognizes certain imported functions and uses checker types (`core/extract-read.ts:1133-1169`) and its VM substitutes module exports by Proxy (`core/extract-check.ts:315-320`). Add contract validation to that path rather than assuming the shared IR handles it. For Effect, use existing service tags and typed service interfaces as the vocabulary; a declared `Effect` environment type is not exhaustive proof of all JavaScript side effects or all transitive services, and `any`/casts can defeat it. The Effect reader's supported operations and synchronous service check are narrower (`core/effect.ts:1-13,217-252`); adapter support for service answers would have to be implemented rather than inferred from a tag.
- **Prior art/risk/cost:** TS decorators/compiler API, Effect services/layers. Roughly 10–20 KB checker and 4–8 KB TS adapter; Effect-specific integration another 6–15 KB. Symbol resolution, mixed JS/TS, bundled module aliases, service provisioning, async effects and separate executor semantics are the main risks. A decorator has runtime cost unless removed; an existing Effect app already pays its own runtime cost, not an added GDP one.

### Python

- **Least:** an existing `typing.Protocol` for the injected dependency, a symbol-bearing contract, and a CI-only `def law(s: Snapshot) -> bool: ...`. For a typed external function, use its annotated signature; `Protocol` removes repeated annotations only when the method has one. A sidecar/`TYPE_CHECKING` design can avoid importing a GDP package at runtime.
- **Mechanism/cost:** use Python AST plus a mandatory mypy/pyright-compatible analysis or checker-produced resolved metadata; static `Protocol` checks structural compatibility but does not inspect the entry's call closure or enforce annotations at runtime. An opt-in decorator can register metadata at import time, but costs a runtime dependency/load work and cannot by itself rule out dynamic calls. A sidecar analyzed without import is zero GDP production cost.
- **Enforcement:** CI source analysis over the entry and resolved helpers plus typechecking; an import-time decorator can only check a restricted, available source closure at load time and cannot guard later rebinding/monkey patches. Reject `getattr` with unknown names, `eval`, dynamic imports, decorators/closures not analyzed, untyped/`Any` call targets and unknown dispatch in the guaranteed mode. `@runtime_checkable Protocol` checks attribute presence, not method signatures or return values.
- **Reader/composition:** `core/py/reader.py:1-5,345-349` already reads annotations without running imported modules and emits external types/patches; add protocol lookup and typed-law AST/manifest. Existing harness patches module/object attributes (`core/py/harness.py:226-245`) and gives stores. Leave inference and comment laws as they are when no closed contract is selected.
- **Prior art/risk/cost:** `typing.Protocol`, mypy/pyright, dependency injection; roughly 10–20 KB analyzer/adapter excluding the external typechecker. Python's dynamic behavior and annotation drift make its guarantee necessarily conditional; annotations alone cannot eliminate tags for unannotated code.

## Build order and falsification

1. **Specify and test the shared contract before inventing macros.** Fix exact call closure, entry/configuration identity, supported intrinsic list, declaration precedence/conflicts, law views and lowering, source-to-key mapping, and refusal semantics. Emit a concise manifest/diagnostic with every assumption; do not persist a stale manifest as authoritative. Preserve the current default and harness protocol. Budget roughly 8–15 KB shared normalization/validation plus tests, before any language checker.
2. **Pilot TypeScript as a required CI analyzer**, not a decorator. Its compiler API and existing Proxy harness make typed symbols and a real expression law accessible without adding a production dependency. Use one small existing-style class with an imported scalar-returning function, a skip and an internal helper. Add a no-emit sidecar, resolve symbols using the real tsconfig, map to current import keys, and feed the existing extraction/check. Its first deliverable can be an independent read-only prototype, not a public macro package.
3. **Falsification bar:** start with a passing rule, then separately add (i) a direct unlisted call, (ii) an unlisted call inside a newly introduced helper, (iii) a call hidden in an unsupported computed/dynamic dispatch, and (iv) a call in a branch never run. Each must fail the required gate at the source location; (iii) must be refused, not silently skipped. Add a declared answer and verify that the actual existing harness receives its exact key and supported typed value; run code and extracted rule, including argument effects and a repeated-callee case that must refuse under today's protocol. Change the dependency signature and a snapshot field and verify type errors; perform an IDE symbol rename and verify both rule and real law references update and re-extract with the correct key. Change only a comment law and confirm it still works without a contract. Verify the emitted production artifact contains no GDP helper/import/law and that omitting or breaking the gate fails CI. If these cannot be achieved on one realistic repository without materially restructuring its rule, stop: typed decorations are not buying the stated guarantee.
4. **Next, only if the pilot earns its keep:** Go, where `go/types` and `go/analysis` give a credible CI pass, and then Python typed-Protocol projects or Java where there is demonstrated demand. Rust is attractive for typed traits but its proc-macro/type-resolution limitation makes a broad guarantee expensive; prototype a deliberately restricted form before promising one. Ruby/Elixir callback signatures are worthwhile only for users who already maintain them and accept conditional type claims. C/C++ and Kotlin compiler integrations should wait for real users and compiler-matrix funding. Effect needs a separate service-semantics pilot, not a claim that environment types cover arbitrary effects.

**Recommendation:** do not build ten macros. Ship the opt-in contract and one or two compiler-aware CI adapters only if the pilot demonstrates that the guarantee survives helper calls, unsupported syntax, renames and the real harness. For most users today's inferred boundary plus the other agent's lightweight comment laws is a better cost/benefit. Macros, annotations, behaviours and generated mocks are useful native *surfaces* where a language supports them; none is a substitute for a fail-closed call analysis, and none removes the need to declare an otherwise unknowable dynamic return type.
