# gdp-wired lean-kernel: kernel.ts checked by Lean

The optional Lean path for the kernel, as `Cert.lean` is for `core/check.ts`: a Lean 4.34.0 twin of `kernel/kernel.ts`
(its tree check, all four of its induction rules, step flags, progress laws, step laws and k-step laws), proven sound, and an exporter that
sends the kernel's real trees to it. `History.lean` adds kernel.ts's history rule, and `Sets.lean` its sets.

| File | What |
| --- | --- |
| `Cert.lean` | A copy of `../lean/Cert.lean`: the derivation checker and `Cert.sound` |
| `Kernel.lean` | Trusted. Terms (var, const, +, ∸, × by a constant, ×, min, max, if, map reads) and conditions (≤, <, =, and, or, not) over naturals. A table names each column: a variable, a map's cell at a key over earlier columns, or a monomial (the product of earlier columns, factors sorted). `checkGoal`: path, Kleene truth, linear forms, facts, leaf rows, claimed cell equalities (re-checked), and leaf products of two rows (p ≤ 0, q ≤ 0 give −p·q ≤ 0, a pair may name an earlier product). Claimed rows are matched by coefficients, then the derivation is replayed by `Cert.check`. The induction rules build their goals in Lean, so kernel.ts's goal builders aren't trusted for them |
| `Progress.lean` | Trusted, on top of `Kernel.lean` (whose theorems it reuses unchanged). **Flags**: step terms read flag f as `.eq (.var f) (.const 1)`; `decideFlags` gives f's variable 1 when its condition holds before the step, else 0. Lean inlines flags itself (`inlineC`: the read becomes the condition, as kernel.ts's goal builder does; `inlineE`: any other read becomes `ite cond 1 0`) and proves inlining keeps the meaning. A machine with flags reaches, outside its flag variables, exactly the states its inlined machine reaches. **Progress**: Lean builds kernel.ts's two goals from the named request (the request is allowed; the step it causes makes `then` hold, primed names read the state and maps after the step) |
| `StepLaw.lean` | Trusted, on top of `Progress.lean`. **Step laws**: Lean builds kernel.ts's goal from the machine (Progress's goal with no request named: the inputs are any ι, the assumption with the flags decided is a hypothesis), so primed names read the state and maps after the step. The exporter inlines flags into `when` and `then`, which must then read no flag variable |
| `Steps.lean` | Trusted, on top of `StepLaw.lean`. **k-step laws**: Lean builds kernel.ts's goal as a symbolic run (a frame: each state variable a term over the first state, each map read a term over the first maps; a step composes the step terms, flags inlined, after the frame, maps read-over-write; before each step the laws, the assumption and that step's `when` at the frame; the j-th request's inputs read by fresh variables, `ren`). One invariant carries the proof: the frame denotes the real state after j steps outside the inputs, the fresh variables and the flags, and the real maps (`Denotes`, kept by `step_denotes`). The exporter sends one `when` per step, flags inlined |
| `History.lean` | Trusted, on top of `Progress.lean` (reusing `fmmachine_sound` unchanged). **Histories** (kernel.ts's `historyMachine`): a machine with maps and flags plus a log of the requests it keeps (`keep`, read with the flags decided). Sums are state variables defined as the sum over the log of a term of the record (`rvars`, the recorded inputs as r.f) and the params; queries are inputs computed at each request as the sum over the log of a term of the record, the params and the plain inputs; relations (when, a, b) with `when` over params and plain inputs and a, b homogeneous over sums and queries. `HReach` is that semantics, sums recomputed from the log and queries from the log before the request. Lean builds the plain machine (`HMachine.plain`: each sum from 0, plus its term at the request when kept; relations conjoined to the assumption) and each relation's record goal (`recordGoal`: a ≤ b for one record, its fields free), and checks kernel.ts's side conditions (`histOk`) |
| `Sets.lean` | Trusted, on top of `Steps.lean`. **Sets** (`SMachine`): maps a request carries (`carried`, any maps at each request), writes at every key (`every`: the value at each key, read with the key bound) and flags that hold at every key (`qflags`, decided classically in the meaning only: 1 when the body holds at every key). Lean builds kernel.ts's closed goals: each quantified flag ?f with `?f ≤ 1`, `?f = 0 ∨ body(t)` at the proof's keys (`qinsts`) and `?f = 1 ∨ ¬body(w)` at its witness (`wits`), the goal reading each step's request as its inputs, its flags' values and a failing key for each witness (`sReq`). A frame denotes the real state outside the extended request and a zone of variables, and the real maps outside the carried ones and the names later requests' maps are read by (`SDenotes`, `sstep_denotes`). The step goal of a law about every key runs from the state with the skolem set, which the machine reads nowhere (`skFresh`, `sNext_upd`). **Functions** are maps no step writes; `facts` are laws over the params and those maps alone: `SReach` starts where they hold, so they hold at every state (`facts_sreach`), and every goal assumes them at the proof's keys (`finsts`), read where the run begins (`facts_frame`). Any machine with functions goes through this file. **Several keys**: an entry may name further keys (`keys2`), variables nothing but laws about them read; it holds at every value of each (`holdsOver`, `SEntry.Holds`: equivalently, at every state that agrees but at those keys), and a frame assumes it at tuples as a law about the first key with the others read as the tuple's terms (`pairLaws`). The start and the step are lemmas (`sstart_case`, `sstep_case`) applied at every value of each further key in turn, which commutes with a step as the skolem does (`fresh_parts`) |
| `Live.lean` | Trusted, on top of `Sets.lean` and `StepLaw.lean`. **Liveness under fairness**: `leads_of_lex` (along any run: if P ∧ ¬Q is kept or Q reached with a rank of naturals never rising in order, and kept only with every region kept; some region holds; and each region's helpful step, taken infinitely often, lowers the rank there; then Q follows every P: a rank that never rises stops changing, `lex_stable`); `primeC`/`primeE` rename a condition's state variables and maps to their primed names, `primeC_eval` reads the renamed one as the condition after the step. Lean builds every goal as a step law from the liveness (`liveStay`, `liveCover`, `liveHelp`, each helpful request's named inputs fixed by its `when`), checks what the liveness reads (`liveOk`, `sliveOk`), and runs (`FRun`, `SRun`) are sequences of allowed steps from a reachable state; `leads_view` is the argument once, for both twins. Under weak fairness (`leads_wf_sound`, maps and flags): each helpful request also proven allowed in its region (`liveAllow`, Progress.lean's goal), so in the suffix where the rank stops it stays enabled, and a request taken whenever it stays enabled comes |
| `Ghost.lean` | Trusted, on top of `Live.lean`. **What a ghost means** (compose.ts's `ghost`): a `Ghosted` machine is the original's parts plus each ghost's start and step, read by no part of the original (`ghostOk`). `ghost_reach`: every reachable state of the original is, outside the ghosts, a reachable state of the ghosted machine, so its ghost-free laws are laws of the original (`ghost_laws`); `ghost_run`, `ghost_run_start`: every run of the original (from the start) lifts to a run of the ghosted machine taking the same requests; `ever_meaning`: an `ever` ghost is 1 exactly when some earlier step met its condition |
| `Refine.lean` | Trusted, on top of `Ghost.lean`. **What a refinement means** (compose.ts's `refinement`): Lean builds the composite from the implementation and the spec, both in the composite's names (`Refined.full`: the spec's inputs read as the witness, each spec part kept where `stutter` holds) and checks neither reads the other's parts (`refinedOk`). `refine_lift`: every reachable state of the implementation is, outside the spec's part, a reachable state of the composite; `refine_project`: the spec's part of every reachable state of the composite is a reachable state of the spec (`spec_view`: the spec's view of a step agrees with the composite's with the witness put in); `refines`: with the relation and the spec's precondition proven of the composite and its step law that the spec allows each request it is sent, every reachable state of the implementation is related by every law to a reachable state of the spec. The same for machines with sets (`SRefined`, `srefine_lift`, `srefine_project`, `srefines`): the sets a request carries shared by name (the spec's among the implementation's), the spec's writes at every key and flags at every key read with the witness put in |
| `emit.ts` | Untrusted, and the package's `gdp-wired/lean`: the kernel's proofs as Lean (columns, rows, cell claims, trees), `toLean` (a file for machines, histories, machines with sets or functions (`smachineToLean`), step laws, loops and decisions; laws with some key go in with the prover's witness in place), `leanProject` (a Lake project with the twin from `library.ts`, generated from these files by `../scripts/gen-lean-library.ts`). Each machine law also gets a plain statement, `<id>.lawN`, over named variables (`ρ «x»`, `μ «M» k`), proven from the twin's theorem through `evalC_iff` (Kernel.lean: a condition's Boolean value is its `holdsC` proposition), so the statement is the law up to unfolding; a law whose terms read an `if` keeps only the twin's theorem |
| `package-check.ts` | `toLean` and `leanProject` end to end on rules written with the builders (maps and a k-step law, a history, a decision, a loop, an escrow with a ghost, the derived authority over sets, quantifiers inside flags and laws, a law with some key, a per-minute limit through `divBy(60)` whose facts Lean proves of `fun x => x / 60` by `omega`, a function of two arguments, the handshake counter whose `pairs` is defined by recursion in Lean (its facts proven there by the definition's equations), the escrow through `Ghost.lean` with its run corollary, the two meter refinements and the lazy authority over sets through `Refine.lean`, the logged ticket queue's liveness through its plain machine, the ticket queue's "every ticket issued is served" through `leads_sound`, batches (two helpful requests, a rank of two in order; with the ticket queue and the logged queue, also under weak fairness), the recounted queue (a history whose query the helpful request leaves free) and the review queue (a machine with sets, through `sleads_sound`), and the normalized scope, a list kept strictly increasing, whose law about every two positions reads in Lean as `∀ k k2 : Nat, ¬(k < k2 ∧ k2 < ρ «Scope_len») ∨ μ «Scope» k < μ «Scope» k2`); `../modal/suite.json`'s `lean-package` runs `lake build` on the result |
| `export-kernel.ts` | Untrusted. Runs `kernel/prove.ts` and writes its trees as Lean data, choosing columns (with monomials), dropping unused rows, renumbering product pairs and claiming cell pairs. Each result is a theorem by `decide +kernel`; tampered proofs appear as `example : check… = false` |
| `Trees.lean` | Everything below except the two largest machines, with the composition examples (`../examples/composition.ts`: two refinements, one stuttering; an interleaving, whose two-turn law goes through `kstep_sound`; an escrow whose ghost remembers a release; the connection pool with its holdings totalled): 486 leaves (a few repeated inside tampered records), 14 tampered proofs computed to false |
| (pruning) | Not in the Lean twin: a history's `prune` goals (a record past its order adds nothing to any query) are about the runtimes, and are checked by the TypeScript kernel only; the laws and relations Lean checks are proven over the whole history either way, so the exporters send the machine without `prune` |
| `SetsTrees.lean` | `export-kernel.ts --sets`: the derived authority (`../examples/sets.ts`) through `smachine_sound` and `skstep_sound`: its 4 laws, 4 step laws and 2 two-step laws (the second request read by `?f@2`, `w?f@2` and `Candidate@2`), each a theorem with a plain statement per law; its proof offered for the variant that keeps the child on a refused derivation, computed to false. 15.5 s on Modal (4 CPUs) |
| `HistoryTrees.lean` | `export-kernel.ts --history`: a sliding-window limit (`../core/models.ts`'s `windowLimit`) through `hmachine_sound`: the window ceiling, 21 leaves with the record goal's; two tampered versions computed to false |
| `TreesBig.lean` | The same plus isolation with others at other providers and the reordered admit migration, both built from admit with the grant as a flag, now passed through and inlined by Lean (`fmmachine_sound`): 1,016 leaves |

The theorems (`#print axioms`: `propext`, `Classical.choice`, `Quot.sound` for each; no `sorry`, no `native_decide`):

| Theorem | Says |
| --- | --- |
| `Kern.sound` | an accepted goal's hypotheses hold for no naturals and no maps |
| `Kern.machine_sound` | scalar step machines: if `checkMachine m ps`, every law holds in every `Reach` state. `Reach.start` needs the precondition `pre`; `preOk` checks `pre` reads no input and no variable the start or a step assigns |
| `Kern.mmachine_sound` | machines with maps: one write per map per step (read-over-write as `if`), maps starting at declared constants, laws about every key proven at a fresh skolem and assumed before the step at the keys the proof names. `pre` may not read maps |
| `Kern.loop_sound` | loops: with `pre` on the params, no infinite run (`¬ ∃ f, f 0 = start ∧ ∀ n, Turn (f n) (f (n+1))`). Invariants hold at the start and each turn keeps them; a tuple of natural ranks drops lexicographically on every turn (`no_descent`: tuples of naturals of one length can't drop forever). Ranks may not read the turn's inputs |
| `Kern.inline_evalE`, `inline_evalC` | inlining flags keeps the meaning: a term or condition inlined, read in a state, equals the original read once the flags are decided (`propext` only) |
| `Kern.fmachine_sound` | scalar machines with flags (`FMachine`): if `checkFMachine f ps` (flag conditions read no flag, laws read no flag, and `checkMachine` of the inlined machine), every law holds in every `FReach` state. Via `freach_plain`: each `FReach` state agrees, outside the flag variables, with a `Reach` state of the inlined machine |
| `Kern.fmmachine_sound` | the same with maps (`FMMachine`, `FMReach`, `fmreach_plain`; writes evaluated with the flags decided) |
| `Kern.progress_sound` | progress over machines with maps and flags: if the laws' proof checks (`checkFMMachine`) and `checkProgress f ps pp` (the request names only inputs, no primed name is an input, `then` reads no flag, and both goals check), then `ProgressHolds f pp`: in every `FMReach` state where `when` holds, the named request (ι := its terms, read in that state) satisfies the assumption once the flags are decided, and `then` holds, its primed names read the state and maps after that step and its plain names the state before (with the request's inputs). `progress_reach`: the state after it is reachable too |
| `Kern.steplaw_sound` | step laws over machines with maps and flags: if the laws' proof checks (`checkFMMachine`) and `checkStepLaw f ps sl` (`when` and `then` read no flag, and the goal checks), then `StepLawHolds f sl`: in every `FMReach` state, every request (inputs ι) that satisfies the assumption once the flags are decided and that `when` admits takes a step where `then` holds, primed names reading the state and maps after it. A history machine's step laws go through its plain machine (`historyMachine`) |
| `Kern.kstep_sound` | k-step laws over machines with maps and flags: if the laws' proof checks and `checkKStep f ps sl` (one `when` per step, the first step reading its own inputs and each later one fresh variables, distinct, read by nothing but `then`; nothing a frame reads touches them or a flag; the goal checks), then `KStepHolds f sl`: from every `FMReach` state, every k requests in a row that are allowed (flags decided) and meet their `when` end in a state where `then` holds, plain names reading the first state and request, `input@j` the j-th request, primed names the last state and maps |
| `Kern.hmachine_sound` | machines with a history (`HMachine`): if `checkHMachine h ps rs` (`histOk`, a checked record goal per relation, and `checkFMMachine` of the plain machine), every law holds in every `HReach` state, sums read as their sums over the log. Via `hreach_fmreach`: every `HReach` state is an `FMReach` state of the plain machine, the relations holding of each request because they hold of each record (`homog_sum`: a homogeneous term over sums of one list is the sum of the term; `sum_le_map`) |
| `Kern.smachine_sound` | machines with sets (`SMachine`): if `checkSMachine s ps` (`sOk`: inputs, flags, quantified flags and witnesses distinct, bodies reading no flag, every quantified flag with a witness; laws reading no request and no carried map; the facts reading only params and maps no step writes or request carries (`factsOk`); the skolem fresh; both goals check), every entry holds in every `SReach` state (a law about every two keys at every value of its second), whatever maps each request carries. A run starts where the facts hold; `<id>_facts_hold` proves them of the functions' Lean definitions where each has one |
| `Kern.skstep_sound` | k-step laws over machines with sets: if the laws' proof checks and `checkSKStep s ps sl` (each later step's inputs, flags' values and witnesses read by fresh variables, its carried maps by fresh map names no step reads; the goal checks), then `SKStepHolds s sl`: from every `SReach` state, every k requests in a row the machine allows, each meeting its `when`, end where `then` holds |
| `Kern.leads_sound` | liveness over machines with maps and flags: if the laws' proof checks, `liveOk`, and the step laws Lean builds from the liveness check, then along every `FRun` that takes each helpful request (its named inputs as its terms) infinitely often, each state where `from` holds is followed (then or later) by one where `to` holds |
| `Kern.leads_wf_sound` | the same under weak fairness: each helpful request proven allowed in its region, and taken whenever, from some point on, it stays allowed |
| `Kern.sleads_sound` | the same over machines with sets (`SRun`): each helpful request names some inputs, the rest and the maps it carries free |
| `Kern.ghost_laws`, `ghost_run`, `ever_meaning` | ghosts: a law of a ghosted machine that reads no ghost holds in every reachable state of the original; runs of the original lift to runs of the ghosted machine; an `ever` ghost is 1 exactly when an earlier step met its condition. The package check uses them to prove, of the escrow without its ghost, that in every run from the start no step refunds after a release (`escrow_no_refund_after_release`) |
| `Kern.refines` | refinements over machines with maps and flags: every `FMReach` state of the implementation is, outside the spec's part, an `FMReach` state of the composite whose spec part is an `FMReach` state of the spec, and every law holds there. The package check proves it of the countdown meter and the two-phase meter (with stutters) against the meter |
| `Kern.srefines` | refinements over machines with sets, as `Kern.refines`, over `SReach`. The package check proves the lazy authority (a release marks the child dead) refines the eager one (a release clears it at every key) |
| `Kern.fold_sound` | folds over binary trees with inputs at leaves and nodes: every law holds of every tree whose inputs meet `assume` (leaf goal, and node goal from both children through per-side copies of the state) |

Tampered, each computed to false: the policy proof on the uncapped machine; gcd without its precondition; pagination
when a page may be empty; the roll-up proof with leaves capped at 51; the admit proof with the Day cap unguarded; an
emptied leaf; the window proof offered for the relation claimed at every t (its record goal fails) and for the relation left out (the ceiling's step goal fails); the bounded_loss tree offered for s ≤ b; the x ≤ x·x tree offered for x·x ≤ x; and a loop whose rank reads
the turn's input (`forever`, below); the flagged policy proof on a flag that always admits; the flagged admit proof on
a grant flag without the Day cap; the in-flight completion proof offered for "with none in flight, one completes"; and
the grant proof offered for "even with the day full". The last two are run-progress.ts's false variants.

**kernel.ts gap found here, since fixed:** `loopObligations` accepted ranks that read the turn's inputs. `forever`
(state x from 0, input w, while x < w, x := x + 1, rank w ∸ x) passed kernel.ts's check, yet the loop runs forever when
every turn sends w = x + 1. kernel.ts now refuses such ranks; the exporter writes `forever`'s rank goal out by hand, it
still checks on its own in Lean (shown in `Trees.lean`), and `checkLoop` rejects it because the rank mentions an input.

On Modal (`../runs/lean-progress-jobs.json`, logs in `../runs/modal/lean-progress/`) both files checked with no
errors, every exported theorem on `propext`, `Classical.choice`, `Quot.sound`.

Not covered by the twin:
- **Flags inside `then`** of a progress law: kernel.ts allows them (read at the request), `checkProgress` refuses them.
  Flags inside a flag's condition are refused by both.
- **Progress over scalar `Machine`s** goes through `FMMachine` with no maps (in-flight is exported that way).
- **The `natural` check** has no counterpart because Lean's terms are natural by construction (constants and factors
  are `Nat`).
- **Histories**: Lean's log holds whole request environments; sums and queries read only the recorded inputs from them
  (through `fieldSub`), as kernel.ts's records hold only those. `histOk` also asks that the precondition read no input,
  flag or field and no map, which kernel.ts's `preOf` already implies for every machine.
- Lean is stricter than kernel.ts in places, never looser: a law may not read a flag, a progress request's keys must be
  inputs and primed names may not be, a product pair that fails to
  multiply rejects the leaf (kernel.ts adds an empty row), and a monomial column must be present for every product
  of two columns a row needs.
